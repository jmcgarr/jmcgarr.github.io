## Read before applying

- **Rule 3 (author's voice):** A, B, C and E change only URLs or attributes. D restores characters the WordPress export ate (noted per item). F is new wording (alt text) and needs your words-level OK. G notes every visible effect. "Remove link, keep text" leaves the words exactly as they are.
- **CR line endings:** 63 content files use old Mac CR line breaks from the WordPress import (43 CR-only, 20 a CR/LF mix); 53 of them are published. The tables mark these files "CR". Any edit must keep each file's existing endings byte for byte (for example, edit with a script that reads and writes bytes; afterwards `file <post>` still reports "CR line terminators" and `git diff` shows only the intended change), or wait for T102/T051. **Line numbers in this report count every CR, LF or CRLF as one line break** (so they match `tr '\r' '\n' < file | cat -n`, not an editor that ignores bare CRs).
- **URLs:** nothing here changes a published URL except H (tag merges, with stubs) and the optional I.4 slug fixes. A and B change outbound links only.
- Each change should be checked afterwards with `./gradlew clean bake`, `scripts/check-urls.sh build/jbake`, and the offline lychee run CI uses.

What a rename costs, per post: a redirect stub at the old path (meta refresh + `rel=canonical`, AGENTS.md Rule 1); the old URL stays in `docs/baseline/urls.txt` (as a stub, so `check-urls.sh` passes); the feed `<guid>` changes, so feed readers show the post as new once; **Giscus comment threads are keyed by the page path** (`post.ftl`), so any comments on the old URL are orphaned; and share counts and inbound links keep pointing at the stub. My suggestion is to leave the slugs and fix only the visible titles if they bother you.

## Appendix: Method

**Date:** all checks ran on 2026-10-09 from macOS (Apple Silicon), against a fresh `./gradlew clean bake` of `main` at `7eced9f` (JBake 2.7, Gradle 9.8.1, JDK 21; 0 warnings). Scripts and raw results stayed in the agent's scratch folder and are not committed; the steps below reproduce them.

**Scope.** Every external URL (`http(s)://` or `//`) in the rendered **body** of each published post and page (`<article>` or `<main>`), in front-matter photo credits, and in the archived comments: 654 link occurrences, 552 unique URLs. The template's own links (menu, footer, share buttons, the default masthead credit) were left out. Drafts were not link-checked. Each URL was mapped back to its source file and line (CR, LF and CRLF all count as line breaks).

**Tools and versions**
- **lychee 0.24.2** (the version CI pins), the `aarch64-apple-darwin` release binary, checksum verified, run online over the URL list: browser User-Agent, `--max-concurrency 8 --host-concurrency 2 --max-retries 2 --retry-wait-time 3 --timeout 25`. **Took 121 s** for 780 URLs (the first list also held the template's share links, which were later dropped). For the 552 content URLs it reported 145 failures (errors plus timeouts).
- **A second checker** (Python `requests`, GET only, browser User-Agent, 8 threads, at most 2 at a time per host, 3 tries with back-off, 10 s connect / 25 s read timeouts, first 64 KB of HTML read for the `<title>`). Lychee doesn't report each redirect hop, so this one recorded every hop to tell permanent (301/308) from temporary redirects, and used page titles to catch "soft 404s" (a 200 that is really "Page not found", a parked or for-sale domain, a redirect to a home page or login wall). It took 236 s, plus 212 s for the `https://` variants of the 423 `http://` URLs, plus re-tries of the timeouts and DNS failures (with `curl` and `dig` as a third opinion).
- **Classification:** OK; permanent redirect (propose the final URL); broken (404/410, DNS gone, connection refused, unreachable on both ports 80 and 443 after 3 tries plus curl, invalid TLS certificate, or a soft 404); check manually (401/403/429/999/5xx, challenge pages, login walls). Every soft-404 and redirect verdict was reviewed by hand; where a page title or redirect target alone decided it, the "Why" column says so.
- **`https://` test (B):** the `https://` form of the URL as written must answer 2xx (directly or via redirects) and end at the same host and path as the `http://` URL does (ignoring `www.`, a trailing slash and `index.html`). Otherwise "leave as is".
- **Wayback Machine:** only the availability API, `https://archive.org/wayback/available?url=<url>&timestamp=<post date YYYYMMDD>`, one request at a time with pauses (the API answered 429 once and returned empty results under load, so every empty answer was asked again in three more slow passes, about one request every 5–30 s; each pass found more, so a few "no snapshot" items may still have one). Of the 167 broken-link items in A.1, 136 have a snapshot and 31 have none. No "save" request was made. For broken images, the snapshot image itself was downloaded (`…/web/<timestamp>im_/<url>`, a GET) to check it and to view it.
- **oEmbed:** YouTube `https://www.youtube.com/oembed?url=…&format=json` for every YouTube embed and link (all 15 videos exist). Vimeo's oEmbed returned 404 even for a known-good video from here, so Vimeo was judged by its player (`player.vimeo.com/video/<id>`: 200 for a control video, 403 and 404 for ours). SlideShare's oEmbed and embed pages answer with a bot challenge, so no SlideShare embed could be verified (a headless Chrome attempt hit the same challenge).
- **Nu HTML Checker 26.10.9** (`vnu.jar` from the GitHub "latest" release, SHA-1 verified) with `--errors-only` on the 307 published HTML files in `build/jbake` (drafts excluded).
- **Images** were opened and viewed one by one (local files from `src/jbake/assets/img/`, hotlinked ones downloaded) before writing any alt text.
- **Tags, drafts and mastheads** come from the front matter of every file under `src/jbake/content/`; draft history from `git log --follow`.

**Network etiquette:** GET and HEAD requests only, plus the public oEmbed and Wayback availability APIs. No logins, no POSTs, no "save page" requests, nothing published. The first lychee pass and the first checker pass also fetched the template's LinkedIn/X share links as plain logged-out GETs (nothing was posted); they're excluded from every count here.

**To reproduce:** build the site, then extract URLs from `build/jbake` the same way (post `<article>` / page `<main>`), run `lychee --no-progress --user-agent "<browser UA>" --max-concurrency 8 --host-concurrency 2 --max-retries 2 --timeout 25 --format json urls.txt`, and run `java -jar vnu.jar --errors-only --format json $(find build/jbake -name '*.html' ! -name '*-draft.html')`. Results for external sites will drift: links rot, bot blocks change, and the Wayback API's answers vary with load.
